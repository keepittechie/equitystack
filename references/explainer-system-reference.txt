==================================================
EXPLAINER SOURCE OF TRUTH
==================================================

Primary files and what they do:

1. lib/explainer-editorial.js
- Main editorial overlay for explainer pages.
- Add the explainer slug entry here.
- This is where category, tags, related explainers, related policies, structured sections, argument mode, and source-context labels are defined.

2. database/explainer_<slug>.sql
- Standard DB import/update script for the explainer row, explainer sources, and explainer-policy links.
- Use the slug in the filename.
- Keep it idempotent with INSERT ... ON DUPLICATE KEY UPDATE where appropriate.

3. app/explainers/claim-map/page.js
- Manual explainer clustering and claim-pattern mapping.
- Update CLAIM_CLUSTERS if the explainer belongs in a visible cluster.
- Update CLAIM_PATTERNS if the explainer answers a recurring claim pattern that should be discoverable from the map legend.

4. lib/public-site-data.js
- Shared assembly layer for public explainer data.
- Important behavior:
  - fetchExplainersIndexData() enriches public explainers with editorial category and tags.
  - fetchExplainerDetailData() resolves explicit related explainers from editorial.relatedExplainers.
  - If editorial.relatedExplainers is empty, the page falls back to same-category related cards.

5. app/explainers/[slug]/page.js
- Public explainer detail template.
- The page already renders:
  - Short answer
  - Argument mode
  - Sources and verification
  - Related explainers
  - Related policies
- Do not redesign this page to add a new explainer.

6. app/explainers/page.js
- Public explainer library page.
- New explainers appear here automatically once the DB row is published and the editorial entry exists.
- Editorial category links are derived automatically from editorial categories in lib/explainer-editorial.js.

==================================================
SHORT ANSWER STANDARD
==================================================

All explainers must include a Short Answer that:

- can be understood in 10 seconds by a non-expert reader
- follows this structure:

  1. what the topic is or what happened
  2. why it matters
  3. what the claim gets wrong OR what the data does not prove

Example pattern:

"[Topic/event] did X. This matters because Y. However, it does not prove Z."

Rules:

- avoid abstract-first language
- define key terms in plain language if used
- avoid multi-clause sentences
- do not assume prior knowledge

FIRST SENTENCE RULE:

- The first sentence must be concrete and easy to understand
- Avoid starting with abstract terms like:
  - policy feedback
  - coalition dynamics
  - disparate impact
- Start with what happened, then introduce the concept if needed

PLACEMENT:

- The Short Answer must appear as the first meaningful content on the page
- It must appear before:
  - Argument Mode
  - Sources
  - Related explainers
  - Any metadata or labels

The Short Answer is the most important part of the explainer.

==================================================
COMPREHENSION PRIORITY RULE
==================================================

When making tradeoffs:

- prioritize clarity over completeness
- prioritize plain language over technical phrasing
- prioritize first-pass understanding over full nuance

Do not remove nuance, but do not lead with it.

The first 10–15 seconds must answer:

- what is this about
- what happened or what is being claimed
- why it matters

==================================================
ONE-CONCEPT RULE
==================================================

Each explainer must focus on one primary concept, claim pattern, or analytical frame.

Avoid:

- combining multiple unrelated mechanisms
- covering multiple eras without a clear throughline
- answering more than one core question

If multiple concepts are needed, create separate explainers and link them.

==================================================
DEFAULT EXPLAINER WORKFLOW
==================================================

For a new explainer, do the work in this order:

1. Check for overlap
2. Add editorial entry
3. Add DB script
4. Wire relationships
5. Update Claim Map if needed
6. Verify locally

(Keep steps exactly as already defined in your system)

==================================================
ARGUMENT MODE GENERATION WARNING
==================================================

Avoid relying on generated or fallback Argument Mode content.

Preferred behavior:

- Write explicit argumentMode content
- Generated content is temporary only

Signs of generated content:

- generic phrasing
- repeated debate lines
- lack of specificity

==================================================
ARGUMENT MODE CHECKLIST
==================================================

Include:

- summary
- quickResponse
- discussionResponse
- debateResponse
- keyPoints
- commonClaims
- debateLines
- shareCards

Rules:

- debateLines must not reuse identical phrasing across explainers
- shareCards must be unique per explainer
- avoid duplication across explainers

==================================================
RELATIONSHIP INTENT RULE
==================================================

When adding relatedExplainers:

- only include explainers that improve understanding
- do not add links just to increase count
- maintain tight conceptual grouping

Preferred:

- 2–5 strong related explainers

==================================================
RELATED EXPLAINER RULES

==================================================
VISUAL EVIDENCE WORKFLOW NOTE
==================================================

When an explainer uses visual evidence:

- bind the visual to a specific claim in the section text
- prefer existing evidence components and UI primitives over custom-designed infographic images
- treat system breakdowns as evidence exhibits, not decorative teaching graphics
- preserve the explainer's existing section flow: claim, evidence, explanation
